## Spatial Memory Milestone

Status as of 2026-09-17: `spatial-memory-v2` has passed focused memory/object/API integration (64 checks), the memory-enabled visual object round trip, measured fixture-region pathway persistence, and all 16 mission browser tests. A separate RTX 5080 fixed baseline passes 18 cases with three unchanged missing-room prerequisites. This is an experimental memory implementation, not demonstrated autonomous learning or faster navigation. [Evidence, hardware provenance and retained failures](DESIGN_PERFORMANCE.md#current-answer).

The candidate extends the existing SQLite MapStore with versioned migrations (current `user_version=3`), opaque environment-instance IDs, layout fingerprints, knowledge profiles, observation events, current entity beliefs, evidence images and immutable checkpoints. Existing map documents remain byte-preserved during migration. Legacy room/object readers use compatibility views; operator reviews are separate from historical observations. Model labels remain tentative and uncalibrated. Objects with the same label are not automatically merged; explicit scoped associations update their current belief while retaining prior events.

The configuration drawer includes Spatial memory: choose a profile, Start fresh knowledge, Save checkpoint, or Fork checkpoint. These operations do not move the robot. Selecting a profile reloads its map unlocalized and clears old local sensor history; fresh knowledge keeps older profiles intact. Forks have independent profile/map identities and retain their checkpoint's evidence and review state. Reset and application restart retain the selected profile; explicit fresh challenge loading or Start fresh knowledge creates a new profile. New missions rotate observation context while retaining knowledge, excluding temporary mission-start destinations from persistence. Saved knowledge never resumes an old route.

Integration points:

- [backend/spatial_memory.py](../backend/spatial_memory.py): migrations, typed scope/evidence, idempotent ingestion, beliefs, queries, frame invalidation and checkpoint forks.
- [backend/memory_session.py](../backend/memory_session.py): bounded background persistence, active-context lifecycle, sensor-grounded ingestion, profile operations and observed-transition collection.
- [backend/home_mapping.py](../backend/home_mapping.py) and [backend/home_mission.py](../backend/home_mission.py): existing maps, places, observations, visits and navigation targets remain the owning structures.
- [backend/worker.py](../backend/worker.py): validated room/object writes, mission-boundary persistence and context changes; existing navigation and collision checks remain authoritative.
- [backend/mission_supervisor.py](../backend/mission_supervisor.py): bounded lookup_room/find_object_sightings/get_search_history/get_exploration_summary actions, search reports and remembered object-viewpoint navigation followed by fresh reacquisition.
- [backend/app.py](../backend/app.py): GET/POST /api/memory, session context validation and optional environment_instance_id on challenge loading.
- [frontend/src/MemoryControls.tsx](../frontend/src/MemoryControls.tsx): profile/checkpoint operations and bounded memory inspection inside the existing configuration drawer.

Current limits: layouts are fixed presets with no generator seed (reported as null); an explicit instance ID can distinguish otherwise identical flats. A changed layout fingerprint isolates a new revision. Automatic legacy imports require internal compatibility approval and otherwise stay separate; no automatic legacy-map transfer is offered in the UI. Frame invalidation marks beliefs and places for revalidation and survives reload; the mapper still has no global loop-closure correction pipeline. Search reports retain viewpoint/surface/entrance scope and visibility limits. A recently checked same-target viewpoint can be deprioritized without declaring the target absent from a room. Stored connections describe sampled measured transitions between annotation neighborhoods, not guaranteed traversability or independently identified room boundaries. SQL result materialization and model summaries are bounded; full persistence/summary cost under load has not been profiled. No automatic pathway shortcut or motor-command replay was added.

## Compact Semantic Mission Contract

`semantic-room-v2` is active following explicit restarts and bounded real-model retests. It extends the `semantic-mission-v1` compact brief with nonblocking moving reviews, stable selected destinations and explicit continued supervision. The latest complete fixed series passes 18 cases with three unchanged missing-room prerequisite blocks. The final real-model attempt still failed kitchen identification/arrival and retained one recovered buffer expiry; this is not fully qualified autonomous room finding. See the [performance ledger](DESIGN_PERFORMANCE.md) for all passes and preserved failures.

Luna receives the original goal, shared evidence/authority rules and mission-specific instructions. The tool schema includes only currently relevant actions and fields. Room missions no longer carry object-box or circuit parameters by default. `explore` delegates destination choice or renews the same active objective; `navigate_frontier` chooses an exact supplied observed frontier ID, not arbitrary coordinates. It reaches one frontier and then asks for another semantic decision. Selecting a frontier does not identify or verify arrival in a room.

Only `mission_local_only` permits local execution without model reviews. A model-produced exploration plan cannot disable supervision, and an exploration-only plan must have an empty target; a named room search requires a room plan even if exploration is needed. New frontier choice is offered only when no mission operation is active. During motion, `review_mode` explicitly asks for continuation or inspection; ordinary retargeting cannot force a stop/new-evidence round trip just to pick the next waypoint.

The current-message `semantic-mission-v1` brief is a projection of AgentObservation plus mission state: paired frame/sequence/pose, head orientation, proximity/contact summary, battery, localization/capture age, current mission-owned task/target/progress, up to two explicitly historical failures, up to four observed frontier choices, named places, recent tentative room observations, receipts and remaining inference budgets. Earlier missions' tasks and navigation statuses are omitted. A running task has current active wording instead of carrying a historical blockage as its current reason. Joints/grippers, long renewal-event histories, map cells and duplicate numeric trail/route arrays are not sent for routine semantic review. Room-report evidence and provenance remain available, with full-precision originals in recordings.

The head PNG and optional observed-map PNG remain paired inputs, both high-detail. Only typed observed-map sensor data may supply the raster; spectator/evaluator geometry is excluded. `sensing` labels capture sequence, monotonic time/age and frame even without a map. Map metadata retains frame, revision, geometry age and uncertainty. The green trail now records worker odometry at 0.025 m displacement intervals, retaining at most 128 points from the current mission and excluding samples newer than the paired camera. It is a recent sampled polyline, not exact continuous swept geometry or a complete lifetime route. `trail_source`, `trail_spacing_m` and `trail_truncated` label that limitation; the raster warns when older samples were dropped. Pink remains the planned route, not proof of executed or authorized motion.

Observed destination selection is revalidated by the sole worker: same mission/run/epoch/map, finite values, capture no older than 15 seconds, stopped-pose displacement <=0.05 m and heading change <=0.08 rad. The worker preserves the point originally offered under the selected ID and validates its current footprint-safe route, rather than requiring it to remain a newly ranked frontier representative. Checks repeat after preparation; the executor cannot substitute a different destination. Stop, expiry, changed ownership or loss of observed clearance invalidates the selection. A different pose-sensitive action during an active review still cancels motion and requests new stopped evidence. Existing short leases, original mission deadline, freshness, collision and bounded retry checks remain unchanged. Generic local exploration's frontier algorithm was not replaced.

Active mission feedback and objective renewal reuse ready asynchronous capture/map results without forcing a synchronous render or waiting for a pending result. The same sensor-age and authority checks apply; a stale result is rejected rather than treated as fresh. Stopped inspection still requests a fresh capture. Frequent objective polling and active feedback use copied lightweight task/localization/coverage state, avoiding full candidate/graph clearance reconstruction. Detailed operator map reads remain available. These changes remove identified blocking operations but do not make the worker hard-real-time or guarantee no buffer expiry.

History retains up to six compact decision/result pairs under the existing byte-estimated context bound; that setting is not a whole-request token cap. Input trace events retain the effective prompt/schema, semantic text bytes and historical-context estimate; operator capability/operation events and recording media retain detailed diagnostics. The trace viewer supports both old full observations and the new compact projection. Full worker timing is still read from operation failures/media, not the model's abbreviated input.

Reported tokens / threshold and requests are visible beside the sticky mission controls, including small screens. The detailed input/output breakdown remains in the mission panel. Thresholds are checked after responses and can be exceeded by one response; incomplete/unreported usage is labelled. This change does not alter review cadence, request limits, reasoning effort, image detail or objective renewal limits. Measured JSON-byte savings are not a provider-token, billing, latency or navigation-quality claim.

## Authorization And Observation Provenance

`expiry-provenance-v1` adds diagnostics without lengthening motion leases or mission budgets. The table below describes full operator/runtime observations and recording events; the semantic brief above deliberately omits detailed authorization histories. There are two authorizations: the persistent exploration objective issued by the mission supervisor, and each short motion buffer issued by the validated navigation runtime. An objective permits fresh planning within its limits; it never makes an expired trajectory valid.

| Payload | Meaning |
| --- | --- |
| `mission.objective.authorization` | Stable operation ID, objective scope, issuer, renewal owner, worker validator, issue/last-renewal/expiry times, last renewal result/rejection, stop and up to 16 recent events. |
| `observation.navigation.diagnostics` | Short-buffer authorization ID, linked task/objective IDs, issuer, renewal owner, original issue/renewal/expiry times and last attempted renewal result. A renewal rejected before issuance has no accepted-command sensor metadata. |
| `last_controller_tick_at_s`, `maximum_recent_tick_gap_s` | Active executor tick timing over at most 128 gaps in a trailing five-second window. Values are retained at stop for later diagnosis; this is not a full-run percentile or sensor-loop timing guarantee. |
| `sensor_at_last_command` | Source timestamp, clock and depth age at the last accepted continuous command. Other executors may report only a navigation ticket with unknown depth age; null never means fresh. |
| `stop` | Time, reason and initiating layer: watchdog, collision monitor, supervisor, controller or external Stop. Attribution follows the code's reason path, not an independent sensor inference. `external_stop` cannot distinguish user, disconnect and takeover without caller-specific instrumentation. |
| `task.route_failures[].motion_diagnostics` | A copy of the ended local buffer's diagnostics before the next route replaces it. Up to four recent failures remain. |

Production deadline comparisons use process monotonic seconds, labelled `clock: monotonic`; mission deadlines have `deadline_clock`/`deadline_at_s`. Simulation seconds measure physics and dwell; Unix seconds correlate recorded events and persistence. Never subtract a simulation/Unix value from a monotonic deadline or compare monotonic values across process restarts. Test-injected clocks are labelled `test` (or an explicit simulation clock where provided). Renewing the objective does not reset the original mission deadline. Timing-only BUFFER_EXPIRED/BUFFER_EMPTY/MOTION_LEASE_EXPIRED failures preserve the frontier for fresh replanning within the unchanged retry bound; actual observed-path failures may reject a frontier. None authorizes an old command after Stop or sensor loss.

### Deadline-Aware Reviews

`renewal-timing-v1` addresses [UC-10](USE_CASE_SPECIFICATION.md#uc-10-continue-safely-during-delayed-supervision) without changing the short motion lease, sensor age limits, travel allowance or mission deadline. The normal 15-second / 2-metre checkpoint remains, but a review can occur sooner when the exploration objective is approaching expiry. Review headroom is `max(10, 1.25 * (recent_input_max + recent_response_max) + 2)` seconds. Input preparation and response durations each retain only the latest eight measurements; a new mission starts with the 10-second minimum reserve. The configured feedback interval still controls when a review may run, including changes made during a wait.

The checkpoint trace reports its trigger (`periodic`, `travel`, `objective_deadline`), remaining objective time, reserve, measured recent maxima and feedback interval. The reserve is a wall-time estimate, not a guarantee. A large feedback interval, short objective, cold capture, unusually slow response or queued worker operation can still consume the available time. Existing request/token limits are unchanged; earlier reviews can consume them earlier and no real-model cost reduction is claimed. Only a valid `explore` reply can renew the existing objective. A `look` or other pose-sensitive action still requires stopping and fresh evidence. An expired objective never resumes from a late reply.

New objective outcomes separate the two previously combined limits:

| Code | Meaning |
| --- | --- |
| `OBJECTIVE_TIME_EXPIRED` | The exploration objective reached its monotonic deadline. Its message also reports travelled distance and the distance allowance. |
| `OBJECTIVE_DISTANCE_LIMIT` | Measured objective travel reached its permitted distance before the deadline. |
| `BUFFER_EXPIRED` | A short local motion buffer was not replaced before its existing validity deadline. This is not model-context exhaustion. |
| `MOTION_LEASE_EXPIRED` | The existing local skill's time budget ended; this is distinct from either objective limit. |

If objective time and distance limits are crossed together, time expiry takes precedence in the reported code. Both retain `authorization_watchdog` at the objective layer and `watchdog` at the motion layer. A Stop arriving during buffer replacement remains `CANCELLED` / `external_stop`, not an internal `EXECUTION_FAILED`.

### Local Worker Timing Logs

New workers keep a bounded in-memory timing ring automatically. Recorded runs save stop snapshots under their existing case directory as `recording/media/worker-timing-<incident_id>.json`; samples in `recording/trajectory.jsonl` link them via `worker_timing_files`. This applies to normal browser mission and home-workflow recordings as well as evaluator recordings. A worker without an attached recorder retains only its bounded in-memory snapshots; no separate persistent timing service or unbounded file stream is started.

- The ring holds 512 recent completed spans/events and eight pending stop snapshots. Its time coverage varies with activity; it is not a fixed five-second window. Stop snapshots are taken after braking and include the run/episode, simulation time, buffer/task/objective IDs, accepted-command sensor data, renewal/expiry/stop information and spans still active at capture.
- Phases identify queued operations, waiting for work, navigation ticks and buffer application, sensing/capture reception, home-map sampling/clearance/path checks, whole-body collision checking, physics/camera publication, recording capture and intentional pacing. Queued-operation names are bounded code identifiers; arguments, images, credentials, object geometry and exception messages are not copied into the timing ring. Supported error codes and exception type names are retained. `Empty` from a nonblocking queue poll is expected control flow, not an execution failure.
- `duration_s` is elapsed wall time, not CPU time. `self_s` subtracts completed, instrumented child spans only. `parent_id`/`span_id` identify nesting; do not sum parent and child durations as independent costs. Queue residence overlaps worker execution and must also not be added to it. In-progress spans use `duration_so_far_s`/`self_so_far_s`; their eventual cost may be larger. Uninstrumented work, OS scheduling and external renderer/GPU internals can remain inside a broad span.
- The recorder transfers at most 128 incidents per recording into its existing bounded pending buffer. The existing background flush writes JSON/media periodically (normally every 0.5 seconds), not from the motion thread. Capturing/copying a bounded snapshot still costs worker time; it is not claimed free. An arrival, deliberate Stop or task timeout also creates a snapshot, so not every timing file denotes failure.
- Inspect `scorecard.worker_timing` for incident, omitted and dropped counts, and the existing `dropped_records` / recording completeness fields for downstream queue loss. Ring eviction and pending-incident loss are explicit counters. A crash before capture/flush or a disk error can lose the unwritten tail; this is not a crash-proof trace journal. The existing 200-event model trace and finalization behavior are unchanged.

To investigate expiry, start from `navigation.stop.at_s`, the matching authorization ID and `expires_at_s`, then examine overlapping completed/active spans and queued work around the last renewal. Do not infer post-expiry travel from a delayed stop timestamp or treat the largest span elsewhere in the ring as the cause. Older runs cannot be retroactively given these phase measurements. [Recorded final Stop example](../.runtime/performance/renewal-timing-v1-final-20260916/cancel-r1/recording/media/worker-timing-1.json), [design and verification](DESIGN_PERFORMANCE.md).

### Cockpit Troubleshooting

`cockpit-diagnostics-v1` makes the existing evidence visible without adding worker requests or changing control policy:

1. **Motion diagnostics** keeps the last buffer stop reason, renewal owner/result, accepted-command sample age, reported buffer status and objective status visible. A later generic cancellation or task token limit does not erase the retained buffer-expiry cause. The robot-status bar still reports the final task outcome separately.
2. **Sensor and timing details** separates the latest depth/map age received from the server from the historical sample age at the last accepted command. Head/proximity/depth frame times are explicitly simulation seconds, not wall-clock freshness. The browser receipt-age counter uses its own monotonic clock; it is never subtracted from server authorization timestamps. Sensor reads reuse SpatialSensing's existing poll, independent of RGB/depth image download success. A missing update, sensor error, disabled sensing or disconnect is labelled rather than presented as fresh. A five-second UI receipt delay is an observability warning, not a new motion threshold. Current idle staleness does not establish what happened during an earlier command.
3. **Authorization timeline** shows the short buffer and exploration objective separately: IDs, owners, issue/renewal/expiry times, stop layer and retained events. `Last tick to stop` is a same-clock interval that can exceed `Recorded max tick gap`: a stall ending at a watchdog stop is not necessarily a completed active-tick interval in that bounded statistic. The stop-minus-expiry interval does not measure how much motion, if any, occurred after expiry. Unknown fields remain unknown, including commands rejected before issuance.
4. **Trace > Failures** selects recorded failed tasks, watchdog/collision stops and error results, not Luna prose or ordinary operator cancellation. Open an input or **Mission operation finished** entry, then a segment, to inspect its frontier, retries, sensor evidence and retained authorization timing. Inputs also expose the recorded laser-sample age, localization method and paired-map capture versus latest-integration age. These are historical observations, not a live sensor stream. Per-cell ages and continuous pose correction must not be inferred.
5. The **Copy motion diagnostics** icon exports the selected current or recorded evidence with its run/session identity where available. It omits spectator geometry and connection settings. **Copy exchange feed** remains the full retained-event export; camera URLs are references, not embedded image bytes. Both exports are bounded by what the backend retained and cannot recover discarded events or identify an uninstrumented blocking worker operation.

No diagnostic read, disclosure, filter or copy issues a motion command. [UI evidence and last-run investigation](DESIGN_PERFORMANCE.md).

### Map Freshness

`observed_map.captured_at` and `age_s` describe the **paired current RGB-D capture**, in monotonic time. `snapshot_built_at_monotonic_s` is when the context was assembled. `geometry_updated_unix_s` and `geometry_age_s` describe the **last integration into the accumulated map**, including accepted depth obstacles; they do not describe the oldest cell. New live-obstacle evidence can also be overlaid onto accumulated geometry. Per-cell observation ages are not retained. Thus a 0.359-second camera age and a 1.532-second geometry-update age need not conflict; neither says all visible map cells were observed within that period. Unix-derived geometry age is descriptive only and becomes unknown if wall time precedes the stored integration timestamp; it is never a control deadline.

### Localization Meaning

Explicit `localize` invokes `HomeMap.match_scan`, which searches candidate XY/yaw corrections around a supplied seed (or searches a larger area without a seed), refines them, and rejects insufficient/ambiguous matches. It reports `method: scan_pose_search`, `pose_correction_estimated: true`. Subsequent tracking is wheel odometry plus `scan_quality` at the supplied current pose: `fixed_pose_scan_consistency`, `pose_correction_estimated: false`, `continuous_pose_correction: false`. The latter evaluates agreement; it does not repair drift. Both explicitly report `calibrated_confidence: false`.

The normal consistency check runs before integrating that call's laser scan. It uses accumulated geometry, which can contain correlated earlier scans/depth, so this ordering is not proof of an independent localization reference. Diagnostics state the evaluation order and reference scan count. Localization `age_s` is time since the last laser sample; `last_consistency_check_at_s` is separate.

A focused real-physics test freezes a sensor-built saved map, obtains a new scan after further simulation, injects odometry error `[+0.20, -0.15, +0.10]` metres/metres/radians and invokes explicit seeded localization without integrating the new scan. The fixed-pose consistency check can accept that offset (residual about 0.173 m, matched fraction about 0.819) without correcting it; explicit search recovered about 0.000154 m position error in this deterministic fixture. The map is verified unchanged. This demonstrates bounded seeded correction against independently acquired data, not calibrated accuracy, continuous SLAM, arbitrary drift recovery or global localization reliability. [Test evidence](../.runtime/expiry-diagnostics-v1/independent-evidence.xml).

### Model Images And Room Evidence

Scenario-derived `environment_id` is retained in full operator map/evaluator metadata but excluded from compact map results and `AgentObservation.spatial`, including subsequent action feedback. Do not put scenario names into model observations to identify rooms. The task's user-requested target remains part of the goal; that is different from revealing the starting room. Operator-provided or previously observed labels remain explicitly unverified hypotheses unless reviewed.

`frame_ref` alone is not image-delivery evidence. The unified supervisor attaches the exact current head PNG as an SDK `input_image` data URL; a boundary regression decodes that URL and compares its bytes with the retained feedback image. When available, the second image is rendered only from the typed observed-map snapshot; raw occupancy cells are not embedded in the accompanying compact observation text. This proves construction of the SDK request in a mocked transport test, not provider-side receipt or correct interpretation. [Boundary check](../tests/test_mission_review_evaluation.py).

When reporting a room identity, `report_observation` accepts explicit `room_label`, `room_confidence` (0..1) and current visual `evidence_text`. The worker requires same-authority, paired image bytes, source sequence, unchanged stopped viewpoint and fresh localized context. It creates/reuses a tentative room-place link at the measured viewpoint and stores label, evidence, uncalibrated confidence, map/room IDs, pose/frame, run/episode, camera/head data, original capture time, Unix observation time, frame reference and image SHA. The image and record use the existing room-observation database; a draft-map report does not silently save or overwrite map geometry. The draft's room-place link remains part of that draft and requires explicit map save for later map reuse; the evidence record alone does not constitute a restorable map.

These records have `review_status: tentative`, `identity_verified: false` and `arrival_verified: false`. They issue no target or return receipt. A generic report without an explicit room label remains a report, not a parsed or fabricated semantic annotation. Correct room identity/arrival still needs separate evaluation; confidence is model-reported, not calibrated. Stale, mismatched-image, moved-view and revoked-authority records are rejected. No existing empty room graph is populated from evaluator geometry or retroactively relabelled.

## Proposed Compute Isolation

Status: **plan only, 2026-09-16**. Design label `map-compute-isolation-v1`. No runtime implementation, new simulation, paid model request, server restart or cloud operation was performed for this plan. The current doorway candidate and failures remain in [DESIGN_PERFORMANCE.md](DESIGN_PERFORMANCE.md). The user requested an explanation and an effort assessment before implementation.

### Recommendation And Evidence

Proceed with a bounded measurement phase, not an unconditional mapper rewrite. The hypothesis is that blocking home-map work delays control refresh enough to explain a meaningful share of missed doorway deadlines. That hypothesis is plausible but not yet established on the current code.

- The previous instrumented corner run recorded 420 clearance-grid calls longer than 10 ms, totalling 8.579 s, and a navigation tick up to 0.672 s against a 0.5 s mapped-motion lease. These are historical, nested/inclusive measurements before the latest cache/vectorization changes. The logger omitted calls <=10 ms, so these samples cannot supply full-run percentiles or additive CPU totals. [Raw timings](../.runtime/doorway-motion-v1/corner-timing-events.json).
- The same run measured the final collision check up to 0.393 s. Offloading map work will not remove that cost. Capture waits, publication/pacing, path tracking and arrival dwell are other possible contributors.
- In the later six-case gate, two of three doorway arrivals missed the unchanged 45 s limit without route-failure records; one reached within about 4 cm of the target but ran out of time during arrival inspection. Another reached the goal in 36.406 s. Buffer expiry is therefore not a sufficient explanation for all remaining failures. [Latest retained motion gate](../.runtime/doorway-motion-v1/final-motion-gate.xml).
- RGB-D rendering and rolling depth-map processing are already asynchronous. The remaining synchronous home-map path performs lidar acquisition, live-obstacle updates, scan consistency, occupancy integration and clearance computation on the physics worker. This is an incremental boundary change, not the introduction of concurrency to a wholly synchronous application. See [worker.py](../backend/worker.py), [home_mission.py](../backend/home_mission.py) and [camera.py](../backend/camera.py).

Worthwhile benefit means more reliable passage within the existing time budget and better control-refresh headroom, not merely fewer milliseconds inside one helper. It does not mean better Luna doorway recognition, reverse maneuver planning, full-house mapping or hard-real-time guarantees on Windows.

Hardware context checked on 2026-09-16: the installed GPU is RTX 3080 (10,240 MiB), alongside a Ryzen 7 3700X (8 cores / 16 logical processors) and 63.9 GiB RAM. While the robot was stopped and its local model unloaded, a system-wide snapshot showed 4,769 MiB VRAM used, 33% GPU utilization, 50% total CPU utilization (busiest logical processor 82%) and 20.9 GiB RAM free. Nine simulator ports were listening. These unsynchronized snapshots do not identify per-process consumption or establish an active-mission hardware bottleneck. The user's prepared RTX 5080 has not been measured. It can accelerate GPU rendering/local-model workloads, but does not automatically move PyBullet, NumPy/SciPy home-map calculations, Python scheduling or remote Luna inference onto the GPU. Phase 0 must record per-process/core utilization and active-render timing, isolate redundant preview load only with permission, and repeat the same frozen tests after a hardware upgrade before attributing benefit to a software refactor. Reassess the refactor if workload isolation or a hardware change already meets the gates.

### Proposed Boundary

The existing physics worker remains the sole owner of simulation, actuator state, motion authorization, sensor acquisition requiring Bullet access, current obstacle evidence, trajectory expiry and final collision checks. Do not move the live simulator or the whole mutable HomeMission object to another thread.

If justified by measurement, first offload **only the pure clearance-grid calculation** from immutable observed occupancy/live-obstacle inputs. The worker publishes an input snapshot; a bounded compute worker returns a candidate mask; the physics worker validates and installs it. Route search, scan matching and occupancy integration are later candidates only if measured independently worthwhile. Route search was relatively cheap in the available historical probe and is not a first target.

The prototype should use one warmed, lifecycle-owned executor, with one calculation in flight and at most one replaceable latest-input snapshot. Prefer reusing the repository's executor/lifecycle patterns. Do not put long home-map jobs ahead of critical RGB-D processing in the existing single-process queue. Compare a thread for NumPy/SciPy work that releases the GIL with a dedicated spawned process, including copy/serialization and startup costs; select the least expensive option that provides isolation. Add no third-party planning framework, service, ROS migration or persistent background worker per request.

Every candidate carries run/episode, map identity and geometry revision, live-obstacle revision, sensor sequence/original capture time, localization-transform revision, footprint radius and Stop/task generation. Results never update these fields to look fresh. New blocking evidence invalidates an older clearance result immediately. Reject stale, reordered, foreign or mismatched results; a job finishing is not permission to move. An old valid trajectory may continue only under its original lease with fresh required sensors and all existing safety checks. If the required mask or corridor is no longer valid, brake. Do not fall back to a blocking calculation while moving or extend authorization to wait for the job.

### Go/No-Go Criteria

These are proposed engineering acceptance gates, not measured results or changed safety limits. Freeze them before executing the comparison.

1. Use all three existing corner offsets/headings, three repetitions each per condition. Run one nominal dedicated-test workload and one bounded load condition representing the observed queue/sensing pressure. Baseline and candidate receive the same load; never stop unrelated user processes without permission. Keep setup, cameras, recorder, path goal, 45 s task limit, arrival tolerance/dwell and scoring unchanged. Pilot with one matched pair first, then run the complete declared matrix only if promising.
2. Candidate must complete all nine doorway attempts within 45 s in each declared workload, with zero sampled contact episodes and complete recordings. Report per-start results and all failures; 9/9 in these fixtures is a development gate, not a general reliability estimate. Stop and closed-door rejection must also pass.
3. Target an active-control accepted-refresh p99 <=0.25 s, providing headroom below the unchanged 0.5 s lease; require no timing-only buffer expiries in the qualification matrix. Measure all intervals, not only slow calls. Explain any pause using an actual safety/task reason, not simply whether inference was pending.
4. On matched successful runs, target at least a 15% reduction in the targeted blocking-time/tail-gap metric, including data-transfer costs, with no worse sensor-age distribution or lower stable-dwell quality. If the baseline fails, prioritize completing the same work over comparing its artificially short elapsed time. Do not count accelerated simulation playback or reduced sensing/recording quality as a speedup.
5. Keep all 18 executable cases passing in the complete fixed household series with the same three blocked room prerequisites. Use `scripts.benchmark_household --stage run --baseline .runtime/performance/doorway-motion-v1-20260916 --design map-compute-isolation-v1 --output <new-directory>`. Do not establish a new series or change input maps/scorers to qualify this candidate.
6. Account for CPU/RAM, executor startup/teardown and depth-renderer contention. Bound queues and memory; verify no orphan process or backlog survives reset/shutdown. A faster helper that starves fresh sensors fails the gate.

### Effort And Stop Conditions

- **Phase 0: small diagnostic change.** Extend the existing probe/test helpers; this is the only immediate implementation commitment. It avoids paying the concurrency cost on an outdated diagnosis.
- **Phases 1-2: medium, bounded prototype.** Limit the prototype to one pure calculation and one executor boundary. Review measured results before expanding beyond it. Copy costs and aggressive map invalidation are the main reasons it may not pay off.
- **Phase 3: higher-risk integration.** Most work is invalidation, ownership, failure handling and tests, not the process-pool call. Do not estimate completion time until phase 0 establishes the actual boundary; a confident calendar estimate now would be misleading.
- If phase 0 points elsewhere, phase 2 returns mostly unusable results, or the fixed motion/safety gates do not improve, stop this approach and keep the synchronous implementation. Remove experimental runtime activation and retain diagnostic artifacts. Do not respond with longer leases, more retries, another planner rewrite or repeated paid-model trials.

Out of scope: a new reverse/trajectory-search policy, diagonal routing (the prior failed experiment stays withdrawn), Luna prompt/model changes, sensor-margin changes, spectator/evaluator inputs, automatic map replacement and cloud deployment. These would make benefit attribution ambiguous and require separate plans. Maintain the design ledger after every future phase and distinguish scripted, operator-guided and real-model evidence.

## Optional Reuse And Local Exploration

**Startup troubleshooting:** `bounded route retries exhausted` can follow motion-lease expiry, no progress or a fresh-map route rejection. It does not establish that the robot is next to a wall. New failures include the last route cause and retain a short history in task telemetry. Keep one current preview where practical; many duplicate enhanced-renderer servers can compete with motion refresh. The [timing investigation](../.runtime/control-timing-20260915-review/summary.md) restored 18/18 executable fixed-series passes after reducing preview load, but its fresh-map diagnostic still stopped on newly observed path obstructions. Do not increase safety timeouts or retry blindly.

In **Challenges > Map source**, choose **Reuse saved environment map** or **Start without saved map**. Reuse is the default and loads the existing map for the exact environment; Reset retains the selected policy. Skipping reuse does not delete or overwrite any saved map. Loaded maps always require fresh scan localization before mapped motion. The challenge dialog and recorded run details show starting map identity/revision/localization; new recordings include its document fingerprint.

Choose **Explore / local** to run the existing sensor-built frontier executive without Luna or any model inference. After an operator Stop, explicitly Resume before starting a new task; Resume never restarts the previous mission. **Start exploration** performs guarded scan/arm preparation, then explores with the selected 1-300 second budget. With a loaded map, localize in Home map first. Without a selected map, it creates a new unsaved sensor draft. Compatible straight-ahead route segments may roll forward with preserved velocity; each is limited to observed footprint-clear space and revalidated by the worker. A clear beam alone does not establish reachability. Unknown space, stale sensors, blocked routes, localization loss, budget expiry and Stop remain terminal or bounded-recovery conditions.

The mode does not guarantee uninterrupted motion, complete coverage, shortest routes or autonomous room naming. A saved-map conflict when publishing a scratch draft is an explicit rejection; the old map is preserved. Load/continue the existing map for persistent expansion. Historical and semantic room labels are not required for geometric exploration.

The [30-second local-only diagnostic](../.runtime/performance/sensor-frontier-exploration-v1-20260915/survey/report.json) travelled 1.175 m, added 5.71 m2 of observed free area and made two rolling continuations with zero model calls, sampled contacts or recording drops. It ended at its budget. The [full unchanged household series](../.runtime/baseline-progress-review/summary.md) remains the capability comparison; the diagnostic does not replace it.

This remains the built-in mapper. SLAM Toolbox's serialized pose graphs, loop closure and resumed SLAM, Nav2 map-frame navigation and explore_lite are a separate migration. Existing occupancy-only databases must not be presented as serialized pose graphs. [Upstream scope and migration boundaries](../.runtime/baseline-progress-review/summary.md#recommended-classical-stack).

## Object Approach

Continuous Built-in control `0.6.0` adds the experimental `object-approach-v1` contract, independently of saved-map storage. Luna uses `select_object` with a current head-image box, a reported label and a base-to-visible-surface stopping distance of 0.4-1.0 m (default 0.8). No motion occurs at selection. The worker measures visible depth surfaces and offers stable `front`, `left` and `right` stopping poses, each with reachable/blocked status from the observed footprint corridor. These are different nearby stopping poses, not a complete set of routes around an object.

`approach_object` selects the existing goal ID and one approach. The local worker refreshes compatible paths at most every 0.25 seconds, preserves that stopping pose and motion velocity, and retains the original path budget, freshness, lease and Stop checks. Object tracking stops at 0.025 m to leave settling margin inside the unchanged 0.04 m arrival acceptance. Unknown corridors, changed posture, revoked authority or expired sensing stop/reject motion. The selected side does not silently change. Only local routes of at most 1.8 m are supported; distant targets still need observed navigation or saved-place memory first.

After reaching the pose, the existing stopped downward perimeter scan observes the parking footprint; the robot faces the surface and takes a new object view. `verify_object` requires a new post-arrival frame, a geometrically consistent visible surface, position within 0.04 m, facing within 0.08 rad, fresh parking clearance and 0.5 simulated seconds of stopped dwell. A changed pose/head view, Stop/task revision or a confirmation older than 15 seconds invalidates current object completion. Surface consistency is not independently verified semantic identity, segmentation or moving-object tracking.

For an object-only task, `finish` with `completion_mode=object`, the goal ID and `entry_confirmed=true` checks that current arrival receipt. For a requested return, Luna advances the subgoal, calls `navigate_place` for the saved Home ID, then uses `completion_mode=saved_place` with that place ID. This verifies a completed same-instruction mapped task, fresh localization, the existing 0.15 m destination tolerance and fresh stopped clearance/dwell. It does not require a room-floor colour reference. A pending unverified object goal cannot be skipped by returning Home. Both completion modes remain agent-reported task completion, separate from independent scenario scoring.

Nav2 does not implement this object contract, and no automatic fallback is permitted. The NavDP/NoMaD study adapters remain separate, stopped-inference experiments. Software checks and all retained failures are recorded in the [design ledger](DESIGN_PERFORMANCE.md); neither these contracts nor a scripted visual fixture establishes reliable arbitrary-object or whole-house navigation.

Qualification on 2026-09-15: 25 object checks and 43 neighboring checks passed. One separately labelled real-Luna table/Home diagnostic passed the unchanged physical criteria in 123.7 control seconds, ending 0.040 m from Home with zero sampled contacts. The full household comparison regressed from 18 passes to 16 passes, two failures and three blocked cases; stable dwell and stale-depth failures remain. Keep the feature experimental. [Measured outcomes, trace and audit](../.runtime/object-approach-v1-review/summary.md).

## Room Memory

Luna now receives the compact named graph, current clearance of each recorded connection path, up to eight reachable frontiers and recent room observations. A blocked recorded path does not establish that every alternate route is blocked. Old graph links without a stored path report unknown clearance.

`observe_room` records the original paired head image, measured map pose, head orientation, run/episode/frame, evidence text and reported confidence. A new room or doorway label is tentative. Existing coordinate-only names are operator-named but unreviewed. Only the connected operator's **Room observations > Confirm** action can confirm a label; Luna has no review capability. Save the map to persist the reviewed place metadata. Room images and review records have separate storage, bounded to 1,000 images per map; the most recent 100 are available for review.

After `navigate_place`, a room match or mismatch requires a new image captured after stable physical arrival at that same destination. The report expires after 15 seconds or a changed base/head view, localization, task, episode or Stop authority. It is always an annotation, never independent semantic proof. The matching report stays in historical room observations after returning Home, explicitly separate from current verification.

For a known-room round trip, Luna supplies `navigate_place(place_id=ROOM_ID, return_place_id=HOME_ID, time_budget=...)`. The worker reaches the room and waits for a fresh `observe_room` match/mismatch. A match starts the guarded Home return; mismatch fails. One original deadline covers both legs and the inference wait. `room_workflow` reports the intermediate and terminal states; completion means the requested physical sequence plus a reported visual match, not independently verified room identity. The manual panel's Navigate action remains single-destination; room-report selection is through Luna's validated capability.

For an unknown room, Luna can choose a supplied `frontier_id` using `explore_frontier` and a 1-300 second budget. The worker revalidates that frontier; blockage stops the selected task without silently choosing another destination. General `explore_map` retains bounded geometric frontier reselection. Both expand only an explicitly writable draft.

**Continue mapping** resumes guided sensing on the loaded map identity. For experiments, set the non-secret `MILO_HOME_MAP_STORE` process variable to a separate working SQLite database before starting the application. The default remains the original runtime store. Never point an expanded-map evaluation at the frozen v1 database.

The separate [room-v2 runner](../scripts/benchmark_rooms.py) copies a store with SQLite backup, retains all camera/physics records and checks original-map/source fingerprints. Its scripted tasks are Kitchen/report/Home, blocked recorded doorway, and unknown-ID rejection. Missing camera-backed room prerequisites remain blocked, not substituted with nearby checkpoints. Scripted room-match reports exercise the contract only and cannot measure recognition accuracy. `--stage survey` performs bounded sensor-only expansion without room labels; `--stage run --map-store PATH` evaluates the separate working map. A saved survey does not imply complete-home coverage.

Current results: two scripted surveys stopped on stale depth before 0.28 m. The published room-v2 baseline has one unknown-ID pass and two missing-room prerequisites. One real-Luna180s attempt travelled8.127m but selected ordinary local actions, recorded no room observations and did not complete the round trip. Its original map remained unchanged. [Reports, provenance and limitations](DESIGN_PERFORMANCE.md#room-memory).

## Scope And Choice

Keep PyBullet, FastAPI, the calibrated head camera, wheel odometry, and the validated physics worker. Add a persistent observed map and a small mission executive beside the existing rolling depth map. No simulator replacement, neural-policy training, cloud provisioning, or mandatory ROS installation.

| Existing component | Inspection finding | Reuse |
| --- | --- | --- |
| [simulation.py](../backend/simulation.py) | Wheel-integrated odometry; paired 160x120 metric RGB-D; measured pan/tilt; current robot-link footprint; eight short-range beams | Sensor source and robot geometry only |
| [ros_navigation.py](../backend/ros_navigation.py) | Simulated 720-ray, 8 m planar lidar already exists | Extracted `capture_laser`; no ROS process required to sample it |
| [spatial.py](../backend/spatial.py) | Rolling 8x8 m depth map, camera extrinsics, observed-floor support, clearance, short SciPy routes; episode-local history | Keep local sensing, calibrated projection and object-surface measurement |
| [worker.py](../backend/worker.py) and [continuous_navigation.py](../backend/continuous_navigation.py) | Sole motion owner; short buffered paths; freshness, collision, expiry, Stop and ownership gates | Execute bounded route segments independently of Luna |
| [continuous_supervisor.py](../backend/continuous_supervisor.py) | Luna selects observed local objectives; no durable home coordinates | Add grounded place selection and compact spatial feedback |
| Recording and NavDP/NoMaD adapters | Recordings contain evaluator state; learned backends have separate observation/goal contracts | Never use recordings or private scene geometry as mapping inputs; keep learned backends separate |

[SLAM Toolbox](https://github.com/SteveMacenski/slam_toolbox) fits the available lidar/odometry and provides pose-graph serialization, loop closure and continued mapping. [AMCL](https://github.com/ros-navigation/navigation2/tree/main/nav2_amcl) fits localization against a saved 2D map. Together with the existing Nav2 bridge, these are the stronger next integration for larger environments. The current bridge uses rolling odometry-frame costmaps, not this saved map. Connecting lifecycle, map server, map-to-odom transforms and cross-scenario localization remains additional work, not a feature enabled here.

[RTAB-Map](https://github.com/introlab/rtabmap_ros) supports RGB-D, stereo and lidar, with appearance-based loop closure and persistent databases. Milo has RGB-D but no stereo pair or implemented visual odometry. Moving-head transforms are available; synchronized visual registration and the native/ROS C++ dependency integration would be additional work. It is not required for the initial planar workflow.

The initial implementation reuses installed NumPy/SciPy for occupancy processing, distance transforms, connected components, scan matching and graph routing. It is an odometry-anchored mapper with scan-consistency monitoring, **not a replacement for full SLAM Toolbox or RTAB-Map loop closure**. The optional Nav2 selector continues to apply to the existing local navigation workflow; saved-home missions explicitly use `builtin_mapped_navigation`. There is no silent Nav2 fallback.

## Operator Workflow

1. Load the intended environment. For reusable household scenarios, select `shared_apartment_v1`.
2. Open **Map > Home map**, then **Start guided mapping**. This folds the arms through the existing validated scan, enables depth, and anchors a new map at the robot's measured starting pose. Select a position on the observed map and choose **Survey to selected point**. The worker plans through footprint-clear space while continuing draft mapping, within the selected task budget. Unknown or blocked points are rejected. The rotation buttons also require fresh sensors and whole-robot clearance. Existing maps use **Continue mapping** after localization.
3. Select **Review map**. Add rooms, doorways and destinations at the current robot position or a selected map position. A name does not authorize an unknown coordinate: annotations must have footprint clearance. Explicit graph connections must have an observed connected route. Room nodes are representative navigable coordinates, not inferred room polygons.
4. Name and **Save map**. A transactional SQLite store permits one initial map per environment. Starting a second initial map is rejected. Existing map revisions are updated with optimistic revision checks; stale writers cannot silently overwrite newer work.
5. Scenario changes automatically discover the same map identity and saved revision. A new worker starts **unlocalized**; no simulator starting coordinates are copied into its map pose. Select a known approximate place, select an approximate map position and heading, or use scan-only search, then **Localize**. Ambiguous or mismatched scans are rejected.
6. Select a reachable named destination and **Navigate**. The executive follows short routes using the saved geometry and current obstacles. Arrival requires position within 0.15 m and a 0.5 simulated-second stopped check. This does not imply the scenario objective is complete.
7. **Expand map** explicitly explores reachable free/unknown boundaries within a 1-300 second wall-clock budget. It modifies an in-memory draft of the same map, not a second map identity. Review and save to publish the next revision and retain expanded coverage/visits/frontier attempts. Closed, blocked and unknown regions remain unexplored. Stop or timeout does not claim complete-home coverage.

An existing map can be loaded after a server restart from the panel. The store uses a local SQLite database under the runtime maps directory; no credential values are stored. Standalone scenarios have distinct map identities by scenario ID. Shared-apartment scenarios reuse `shared_apartment_v1`. If an environment's physical layout is intentionally changed, give that environment a new version instead of pretending it is the same house.

## Ownership And Representations

[home_mapping.py](../backend/home_mapping.py) owns the map, coordinate transforms, named graph, scan matching, frontier bookkeeping and transactional storage. [home_mission.py](../backend/home_mission.py) owns mapping stages and mission state. The physics worker owns sensor sampling and every actuation.

| Representation | Contents | Lifetime |
| --- | --- | --- |
| Geometric map | 0.1 m cells: unknown, observed free, occupied; ray evidence and measured depth obstacles | Saved, versioned, read-only during ordinary navigation |
| Named graph | Operator labels, room/doorway/destination type, map-frame pose, explicit validated links | Saved with map |
| Live obstacle layer | Recent lidar hits and head-depth obstacles, free-ray clearing, 2 s expiry | Per worker; never silently persisted as scenario geometry |
| Coverage/history | Observed area, visited cells, frontier attempts and knowledge count at each attempt | Retained in draft; persisted on Save |
| Object observations | Measured visible-surface position, label, timestamp, reported confidence, run/frame provenance and original PNG | Separate SQLite records and images; geometry unchanged |

Frames: `map`, `wheel_odometry`, `robot_base`, `laser`, calibrated optical camera. Coordinates are metres, yaw/pan/tilt radians. The map-to-odometry transform is established from scans after restart. The lidar is fixed to the base; depth projection uses the **corresponding frame's** measured head pan/tilt and odometry. Persistence uses Unix timestamps; control leases and task deadlines use monotonic time. Every map has an environment identity, UUID and revision.

Luna receives only `AgentObservation.spatial`, a compact observation-derived summary with reachable places, pose quality, progress and failures. It does not receive the occupancy array, spectator geometry, scorer state or hidden object coordinates. New actions are `navigate_place`, `explore_map`, `spatial_state`, `cancel_task`, and `remember_object`. Place IDs must come from the supplied summary. Delayed moving selections expire after 15 seconds. The executive runs without further inference while executing an accepted task.

Object labels and confidence are supplied annotations, not verified recognition. `remember_object` projects a normalized box in the paired camera image onto visible measured surfaces, never the simulator's object center. The original image is retained. `currently_observed` requires the same current run, episode and sensor sequence plus age <=2 seconds; otherwise the UI says **Last seen**. No automatic detector, identity association, object-motion tracker or recognition-accuracy claim is included. `ObjectMemory` is an extensible storage protocol.

## Safety And Limits

- Planning inflates occupied **and unknown** space by the current robot footprint plus one grid cell. The initial robot support disk is an explicit flat-floor/proprioceptive assumption, matching the existing local planner's bootstrap concept; it is not an observed corridor.
- Live depth is required before and during motion; lidar/pose data must be fresh. Pose jumps, insufficient scan returns, ambiguous localization, mismatched scans and missing sensors stop or reject motion. Scan residuals are diagnostics, not calibrated covariance or proof against all perceptual aliasing.
- Enhanced mapped sensing renders immutable paired RGB-D snapshots outside the physics thread. Accepted depth can update live obstacle checks before rolling-map processing completes; each retains its original timestamp and measured camera pose. Stop, episode and sensing-generation checks discard revoked in-flight frames. The processed rolling map is never retimestamped to pretend it is newer.
- Raw mapped capture may continue during a pending map job; at most one capture and one map job are in flight. Extra raw frames update only live sensing until the map processor becomes available. Batched depth projection and lidar cell-ID deduplication preserve the exact original cell-update rules.
- In mapping mode, raw manual drive/rotation is guarded before motion and every 50 simulated milliseconds by current localization, depth, observed predicted footprint clearance and the existing whole-robot shield. The UI uses planned `guided_to` waypoints for translation. Non-mapping manual drive remains the original direct-control path, not a sensor-qualified autonomous controller.
- The existing whole-body simulator clearance shield remains a final, privileged safety check. It is not used to construct the map or select destinations. Thus these tests are not evidence of a hardware-ready sensor-only safety system.
- One local segment is at most 1 m, existing speed/acceleration caps remain, and mapped motion leases expire after 0.5 seconds without refresh. At most two stopped replans share the original mission deadline. Stale required depth and localization failure remain terminal.
- Arrival waits for a full 0.5 simulated seconds of measured stable odometry after settling, within the task deadline and a two-second settling bound. Safe braking time does not count as an already stable dwell. Far-object AABB filtering reduces expensive exact collision queries without changing nearby checks or margins.
- Stop, takeover, reset, disconnect and changed task revisions invalidate pending motion. Resume can resume sensing but cannot resurrect a cancelled mission. Manual relocation invalidates localization.
- The current map is bounded to 40x40 m, assumes a flat floor and has no loop closure, map deformation, multi-floor support or calibrated drift covariance. Long guided paths can accumulate odometry error. Re-localize from a stopped known area when needed. Larger-home reliability remains unmeasured.
- A planar scan can miss low/high objects. Head depth and the existing safety shield supplement it. A moving item observed during initial mapping may become a conservative stored obstruction; ordinary scenario navigation does not erase that obstruction.
- Frontier selection is geometric, with at most 20 candidate groups. Two attempts without 25 additional known cells suppress a repeated frontier. A named room region currently means within 3 m of that room's annotated coordinate, not an inferred room boundary. Expansion is bounded and experimental, not guaranteed coverage or shortest exploration time.
- Unsaved mapping/annotation/expansion edits remain drafts and are not crash-recovered. Saved maps, visits and attempt history survive restarts. Whole-home coverage percentage is intentionally unknown because no hidden floor plan supplies a denominator.

## APIs And Scenario Tests

`GET /api/home` returns operator map state. `POST /api/home` accepts `run_id`, `episode_epoch`, `action`, and bounded action fields. Actions: `start_mapping`, `review`, `save_map`, `load_map`, `localize`, `add_place`, `navigate_to`, `explore`, `get_spatial_state`, `remember_object`, `cancel_task`. Mutations require the connected operator and exclusive control. Existing same-origin protection applies. Worker calls additionally bind Stop/task revisions and reject mismatched map identity.

The existing scenario evaluator accepts an explicit saved map without remapping:

```powershell
./.runtime/env/python.exe -m scripts.evaluate_supervised --mode luna_continuous --stage challenges --environment shared_apartment_v1 --challenges apartment flat_kitchen recharge --home-map-id MAP_UUID --localization-place-id HOME_PLACE_UUID --time-limit-s 180 --design persistent-home-map-v1 --output .runtime/performance/NEW_RUN_DIRECTORY
```

Omit the localization place for scan-only search, or use `--localization-pose X_M Y_M YAW_RAD` for an approximate operator hint. Never obtain that hint from evaluator/simulator object coordinates. Localization setup time and seed source are recorded separately. Each trial records map UUID, revision, document SHA-256 and localization quality. The evaluator disables expansion so the saved map remains a matched, frozen input. A failed localization ends the setup; it does not silently create a fresh map. This command uses configured real inference and was **not run** as part of the software implementation.
