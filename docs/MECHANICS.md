# Mechanical Slice

## Ownership and Timing

The opt-in `supervised_policy` mode is an exception to the original rendering path below: a worker-owned left-arm task executor accepts local SmolVLA action chunks, while a separate snapshot process renders 320x240 paired head-camera feedback. Supervisor and policy inference are independent. See [SMOLVLA.md](SMOLVLA.md) for contracts, limits, freshness, and the trained-checkpoint gate. No additional process can actuate the authoritative Bullet client. Single-step and navigation retain the original timing behavior described here.

`SimulationWorker` owns one serialized thread. It initializes, executes, renders, and disposes `BulletSimulation`. FastAPI awaits concurrent futures; it does not execute physics on the event loop. A thread-safe event interrupts motion at a physics tick without waiting for the command queue. Reset closes the old worker before constructing the next episode.

Policy motion uses `PolicyPacer` with absolute high-resolution deadlines. A requested Windows 4.2 ms event wait was measured taking about 19 ms, causing former per-tick relative sleeps to accumulate and expire valid chunks. The pacer accounts for oversleep using subsequent ticks, rebases after more than 50 ms of lag or a motion-revision change, and resets on an empty buffer. Waits remain interruptible; each physics tick still checks cancellation and unmodified chunk/skill wall-clock deadlines. Fixed 1/240 s integration, collision checks, snapshots every 12 ticks, and the single motion authority are unchanged. This improves aggregate pacing but does not guarantee evenly spaced or hard-real-time ticks. See [SMOLVLA.md](SMOLVLA.md#windows-policy-timing-fix) for measured before/after reports.

Each episode owns an authoritative dynamic PyBullet DIRECT client and a private, unstepped, fixed-base planning client. The planner receives copies of state for kinematic/collision validation. It is not a second authoritative simulation, and no frontend physics is used. Spectator geometry comes from the same generated URDF visual shapes as the physics robot, with server poses applied to links.

Physics advances at 1/240 s only during commands or a valid navigation buffer (`step_locked` outside those intervals). Live manual and model-directed execution is wall-paced by the worker. State snapshots publish every 12 ticks (20 Hz simulated); the operator head-camera preview targets 10 Hz wall-clock capture during commands, with initial and final frames also published. Actual throughput depends on CPU rendering and browser delivery, not a hard real-time guarantee. Navigation mode permits bounded motion during inference, not free-running physics after a buffer expires. The final browser disconnect sets the stop event; reconnect does not automatically resume motion.

Preview capture runs on the physics worker through `capture()`, without calling `observe()` or changing model observation sequences. A separate 16-frame cache serves run-scoped `/api/camera/{run_id}/{reference}` PNGs with `no-store`; reset invalidates old URLs. The browser keeps the last decoded image while loading one replacement at a time and skips intermediate previews when delivery is slow. Model feedback still captures its own paired observation/image at scheduled boundaries, and the exchange feed retains those exact inputs independently. Spectator poses and preview metadata remain operator-only.

Chat and Voice selection is server-side operator state. `POST /api/agent/mode` validates the run ID/epoch, stops the worker, and awaits controller cancellation before changing modes. Text starts and `POST /api/agent/chat` require Chat; new voice sockets require Voice. Existing same-origin, exclusive ownership, operator-connection, and stale-episode checks apply. Leaving Voice unmounts the audio client immediately while server cancellation finishes. Mode selection never starts inference or recording by itself.

Chat reuses the Responses controller and canonical tools. A strict `ChatStart` adds a nonblank message (maximum 2,000 characters) and optional prior conversation ID. Follow-ups validate that ID and episode before retaining complete model/tool turns within the selected estimated token budget. Each message is serialized, captures fresh robot feedback, and gets the existing response/time limits; text-only replies finish without motion. The active typed request remains in the current goal even with zero retained history. Visible user/assistant messages are bounded to 40 entries. Other than the user's text and public goal, world inputs remain restricted to `AgentObservation` and its paired head image. Chat and Voice histories are not merged.

`backend/feedback.py` serializes model-facing sensor values, tool results, and recent-action summaries with at most three decimal places and no JSON whitespace. Whole numbers and negative zero are normalized; integer identifiers, strings, and booleans are unchanged. Physics, validation, safety thresholds, raw API observations, and executed commands retain their original precision. Rounded zero is not proof of zero movement. Compact tool replies retain status/errors, duration, measured deltas, observation sequence, and collision feedback instead of repeating the full observation and action ID; fresh paired camera/sensor feedback follows separately. Recent actions omit redundant timestamps, descriptions, and durations. Image detail remains high. The exchange feed shows the rounded sensor payload, detailed result, and exact compact reply sent to the model; numeric compaction applies to Foundry, Ollama, and Realtime voice.

Text control uses `AgentStart.images_per_request` (1-8, default 1) and `context_tokens` (0-32768, default 4096). `camera_batch` includes the current paired observation/image first, then distinct historical pairs selected from the controller's last eight feedback observations, ordered by capture timestamp. Repeated PNGs are omitted, so the batch can be smaller than requested. No spectator or live-preview cache metadata is used. Historical pairs carry the explicit `historical_camera_observation` label; only the current observation can authorize motion. The charging preset reserves one historical slot for its initial view when the image limit is at least two and that view differs from the current image. New runs/reset clear camera memory; valid typed follow-ups and idle wake retain it within the same episode.

`retain_context` removes image parts from saved turns and retains the newest whole turns that fit the remaining budget after recent-action summaries. A conservative cross-provider text-token estimate counts UTF-8 JSON bytes plus 16 units per message; this is deliberately not billed token usage or a model-specific tokenizer count. The budget excludes current inputs, tool schemas, instructions, and the selected camera pairs. Zero omits historical text and summaries. Trimmed turns are removed from memory and cannot reappear after increasing the budget; a 200-turn guard bounds object count. The trace records the effective budget, estimate, actual image count, and each image's frame/time metadata. Indexed trace image URLs share session/retention/reset checks with the original single-frame URL. Voice remains on its existing Realtime conversation handling.

## Reactive Navigation Execution

`AgentStart.execution_mode` defaults to `single_step`. `navigation_plan` selects five tools: `set_navigation_plan`, `replace_motion_buffer`, `complete_navigation_skill`, `observe`, and `stop`. The first three have strict contracts in `backend/navigation.py`; `/api/tools?execution_mode=navigation_plan` exposes the same schemas. Foundry and Ollama share the executor and rules. Standard tools and manual operation retain their previous contracts. No manipulation tool can run while navigation owns motion.

Plans contain one to eight steps following the repeated order inspect_room, locate_doorway, approach, cross. The runtime tracks pending/running/completed/failed/cancelled states. Replacing a plan brakes and cancels its remaining skills before beginning the new plan. Inspection permits head segments only; locating also permits pure base rotation. Completing either requires at least 0.4 rad of measured head-plus-base scan. Approach and crossing require at least 0.1 m net encoder translation, no current contact, and an evidence string from the model. These are mechanical preconditions, not a visual doorway classifier. Travel is capped at 2 m per approach and 1.5 m for other skills. Each active skill has a 60-second wall-clock deadline.

The worker advances navigation in slices of up to 12 physics ticks and accepts queued operations between slices. A buffer contains one to four segments of 0.2-1.0 s each, up to 2.0 s total, controlling either the head or the base. Base limits are 0.15 m/s and 0.5 rad/s, with target-velocity slew limits of 0.3 m/s squared and 1 rad/s squared. The remaining horizon also ramps velocity down before buffer exhaustion. Replacement keeps the current velocity and changes only future setpoints. There is no new free-running physics thread or second motion authority.

`AgentObservation.navigation` reports only the submitted plan and its measured execution telemetry, not scene/evaluator geometry. Feedback creates a worker-owned ticket binding observation sequence, plan revision, capture time, and encoder pose. Updates must provide the current revision. A moving observation expires after 2 s; a stationary one after 45 s. Either is rejected after more than 0.25 m encoder translation or 0.35 rad heading change. Exhaustion, replacement, skill transition, Stop, and faults invalidate earlier tickets. Old observation IDs are not silently reassigned to new state.

The controller compares both remaining simulated motion and remaining wall-clock lease against a low-water threshold of `min(1.5, max(0.75, last_inference_latency + 0.25))` seconds, while respecting the selected minimum feedback interval. If the estimated inference latency plus 0.25 s cannot fit the available window, it waits for the buffer to brake before capturing feedback and planning from rest. Faster inference can still run concurrently with motion. If expiry or exhaustion changes the revision during inference, the outdated request is cancelled and awaited before capturing fresh feedback; its tool calls are never submitted. These retries count toward the existing turn/session limits, but not toward the three-consecutive-invalid-tool-update limit. Navigation retains complete turns within the same selected text budget as single-step mode; the latest observation contains the current plan state. Inference remains serialized.

Before each slice, the worker checks fresh proximity/contact data, supporting floor contact, and base tilt within 0.25 rad. Whole-robot collision preflight samples a 0.4-second lookahead at four points for both requested and current velocity, using a 15 mm scene clearance and the floor footprint. Translational distance beams below 0.18 m also stop motion. The private planning client is used internally for safety; object identities and coordinates are not returned to the model. This conservative constant-velocity sampling is not a complete dynamic planner or certified stopping-distance guarantee.

The buffer wall-clock lease is its submitted duration plus 0.5 s (at most 2.5 s), unchanged by slower rendering or model latency. Both lease expiry and normal exhaustion brake, discard pending motion, and invalidate tickets, leaving the active skill awaiting fresh feedback; neither is task completion or a fatal plan error. A local feedback gap over 0.75 s, contact/clearance/stability failure, execution exception, or skill timeout still brakes and fails the active skill. Later steps are cancelled. The original 60-second skill deadline is not renewed by buffer pauses. Stop remains independently checked each physics tick, and its cleared buffer is published immediately. The controller notices worker failure while waiting for a model and cancels that request without waiting for its ordinary timeout. Ended navigation runs do not arm automatic camera wake. These software mechanisms depend on the worker making progress and do not establish hardware emergency-stop safety.

## Idle and Camera Wake

Completed text/chat tasks arm a separate, cancellable local watcher after the inference client closes. Successful scenario completion/failure stops goal-driven continuation; a `stop` tool may supply `task_status` (`completed` or `unachievable`) and a reason. Text-only replies also arm the watcher. Voice arms it after a final reply, preserving the existing open connection. Errors and hard operator interrupts do not arm automatic retries.

The watcher samples `capture()` on the serialized worker every 0.5 s without calling `observe()` or stepping Bullet. RGB images are resized to 64 x 48; a change means at least 1% of pixels differ from the last meaningful reference by more than 12 levels in any channel. The reference is retained across sub-threshold noise so gradual changes can accumulate. These thresholds are a local motion heuristic, not semantic understanding. Only a changed sample publishes a new operator preview.

After at least five wall-clock seconds since arming and since the last meaningful image change, a completed task enters `sleeping`. Joints remain held and wheels braked; the programmatic stop latch is released only if the worker's stop revision is unchanged. No inference runs in idle. A new camera revision wakes once, then disarms that watcher while fresh feedback is processed. Text wakes reuse session ID, token totals, bounded history, seen call IDs, feedback pacing, remaining turn budget, and original deadline. They do not create unlimited fresh sessions. Voice camera wake is enforced with tools disabled and does not record audio.

New Chat/Voice interaction cancels the watcher before user-requested control. Stop revisions and cancellation checks protect queued resume and wake operations. Stop, takeover, mode changes, reset, disconnect, and text-model reconfiguration invalidate watchers; no camera event may resume their canceled motion. Camera-monitor failure stops control. Watcher metadata is operator-only and is never inserted into `AgentObservation`; model inputs remain real paired observations/images plus user text. Physics stays step-locked, and there is no camera-change trigger from spectator-only navigation.

## Coordinate Frames

- World and base: x forward, y left, z up at zero heading.
- Base origin: chassis center, approximately 0.155 m above a level floor.
- Quaternions: x,y,z,w. Accept norm within 0.02 of one, normalize it, and reject all other/degenerate inputs.
- Head camera: rigid offset `[0.095, 0, 0.005]` m from head link frame; forward is head +x and up is head +z. Positive head pitch tilts down.
- Camera optical: right = head -y, down = head -z, forward = head +x.
- Three.js spectator: a -pi/2 rotation around x maps `(x,y,z)` to `(x,z,-y)` in the y-up renderer. Bullet cylinder z axes are explicitly converted to Three.js cylinder y axes. Desktop/mobile renderer and motion checks use real canvas pixels.

The camera is rendered with Bullet TinyRenderer at 640 x 480, vertical FOV 65 degrees, near 0.015 m, far 12 m. There is no depth/segmentation payload in agent observations. Camera self-occlusion uses the robot's actual geometry. Spectator orbit controls cannot change the camera transform on the backend.

Both arms attach to the torso through fixed shoulder brackets with matching visual and collision geometry. Each bracket bridges the torso to the shoulder pivot at `[0, +/-0.25, 0.245]` m in the base frame. These pivots, joint axes, link lengths, and calibrated palm targets are unchanged. Collision preflight includes both brackets; only the first two joints' intentional overlap with their own mount is excluded.

## Surface Materials

`backend/materials.py` deterministically generates six original 512 x 512 RGB PNGs into `assets/textures` when missing: concrete, plaster, wood, tile, fabric, and stone. Scene names select materials; task cubes and goal markings retain their identifying solid colors. PyBullet applies the maps to authoritative visual shapes, and geometry metadata supplies the same allowlisted `/api/textures/{name}.png` URLs to Three.js. The renderer disposes textures on scene replacement and adds soft shadow mapping. UV mapping and lighting differ between renderers, but geometry, surface patterns, and physical state are shared. Materials do not change friction, collision geometry, or task scoring.

## Proximity Sensors

`AgentObservation.proximity` contains eight `DistanceReading` values and a list of directional `CollisionReading` forces. Rays are cast in the authoritative Bullet client at 45-degree intervals around the base frame, starting at the rectangular sensor envelope (x +/-0.18 m, y +/-0.25 m) and z=-0.115 m relative to the base. Readings are distance from each mount to first hit, rounded to millimeters, with a 2 m maximum. They rotate with the robot. `clear` and `occluded` return a null distance, distinguishing no hit from self-occlusion. A beam at one low height cannot represent the full arm/body swept volume or guarantee obstacle clearance.

Contact sensors group physical normal forces above 0.05 N into front/left/rear/right using the robot-local contact position. They exclude self-contact, floor contact, and finger-to-movable-object grasp contact, but include finger contact with static obstacles. The existing `bumpers` list now contains these contact directions instead of flagging every chassis contact. Only directions, bearings, distances, status, simulated timestamp, and forces are serialized; hit bodies and positions remain private.

The worker publishes a separate operator `proximity` snapshot every 12 physics ticks and after actions/placement. This does not advance observation sequence or increase model feedback cadence. Single-step actions also retain the peak directional contact forces sampled every 12 ticks (20 Hz simulated) in `sensor_deltas.contacts_during_action`, so contact that clears before the final observation can still reach the model. This is a sampled peak, not every instantaneous impact. The accumulator resets for each action, including cancellation. It exposes no object identities or world coordinates.

Model inputs include concise collision guidance derived from those measurements. Current contacts take precedence over historical contacts; front/side contact suggests inspecting rear clearance and considering a short, slow reverse, while current rear contact explicitly forbids reversing. Distance beams alone do not establish clearance. Cleared action contacts are labeled `during_action` rather than reported as current contact. A rejected preflight is not fabricated as a physical collision. Advice does not execute motion, release Stop, or override navigation safety failures. Actual recovery remains a model decision through the validated executor.

After an otherwise successful `drive_base`, the simulator reports `NO_PROGRESS` when the final bumper/contact list is nonempty, the request magnitude times elapsed simulation time is at least 0.02 m or 0.08 rad, and encoder translation is below 0.005 m and heading change below 0.02 rad. The action has already run and braked; its actual duration and observed encoder deltas are retained. Zero-motion waits, observation/head movement, and successful retreat remain available. The heuristic uses no evaluator pose, cannot reliably detect wheel slip, and is not predictive obstacle avoidance.

The text/Ollama controller summarizes its last three completed actions into the latest feedback message, alongside the corresponding camera and observation, and records the same summary in the trace. The summary is not stored again in rolling model history, preventing recursive duplication. Three consecutive `drive_base` results with `NO_PROGRESS` stop that controller with an error and no automatic wake. This does not establish semantic recovery or add equivalent retry counting to Realtime voice, which still receives the underlying tool error. The worker publishes final observation/result and `busy=false` together to avoid reporting a completed observation as in-flight.

## Outcome Feedback

Text and Voice controllers retain an operator-only outcome record with kind, reason, source, and timestamp. Sources distinguish `physics`, `agent`, and `controller`. Reported completion/unachievable states do not alter private evaluator scores. Controller errors, limits, interruptions, and text-only endings have separate classifications. Outcomes persist through idle, reset on a new request or automatic reassessment, and retain explicit operator interruption reasons.

The result band uses current scenario checks for green verified completion, marks manual-placement intervention, and exposes reported outcomes without presenting them as verified success. Newer tool results can supersede older controller reports. Disconnection and errors override success, reset clears outcomes, and losing scenario conditions removes the success banner. The feedback is local current-state reporting, not a persistent run journal.

## Controls and Limits

The canonical registry is in `backend/contracts.py`; `/api/tools` publishes its JSON Schemas, descriptions, limits, and units. `/api/calibration` publishes joint names/axes, limits, neutral poses, wheel geometry, and an asset hash. `finish_task` and `submit_answer` contracts are defined but are not enabled by these presets. Challenge progress is computed privately from physics and displayed to the operator; a model's summary does not establish success.

- Base commands: at most 0.3 m/s, 0.8 rad/s, and 2 seconds, with a 0.3-second wheel-speed ramp at both ends and 5 Nm wheel motor force limits.
- Arms: six joints each, 1.8 rad/s velocity and 24 Nm force limits. Joint targets exceeding rate/position limits are rejected.
- Head: yaw [-1.5,1.5], pitch [-0.7,1.15] rad, 5 Nm motor force and 1.8 rad/s servo limit.
- Gripper opening: 0 to 0.11 m, with fingers limited to 0.15 m/s and at most 35 N each.
- IK endpoint tolerance: 8 mm / 0.08 rad. Cartesian execution tolerance: 15 mm / 0.1 rad under motor load.
- Cartesian commands snapshot the base frame on acceptance, solve a sequence spaced at most 15 mm apart, validate joint velocities and collision samples before moving, then servo the sequence. They do not search for an alternative route around an obstacle.

The visible palm origin is the grasp center. To reach the curated left floor cube from the initial base pose, use `[0.36,0.25,-0.12]` m with quaternion `[0,0,0,1]`, duration 2 s. Close the left gripper at 20 N, then move the palm to `[0.36,0.25,0.05]` m over 2 s. Open to 0.11 m to release. Right-arm physics tests use a mirrored cube at y=-0.25 m; the default manual bench currently spawns only the left cube.

## Manual Placement

The spectator raycasts visible robot meshes using the operator-only `robot_body_id`. A selected robot is previewed with a translated Three.js group on the world floor plane; the physics scene and camera do not change during the gesture. Background gestures retain OrbitControls. Pointer capture supports mouse and touch; cancellation, Escape, stop, disconnect, a changed observation, or a replaced episode clears the preview. Arrow keys provide 0.1 m world-X/Y steps, with Enter to commit.

`POST /api/robot/placement` accepts a strict `ManualPlacement` containing run ID, epoch, observation sequence, and finite world X/Y coordinates. This route is separate from the model tool registry, requires idle manual ownership, and executes through the serialized worker. It rejects stopped/stale requests and active assisted grasps. The synchronized planning client checks all robot links against the floor footprint and destination obstacle penetration before authoritative mutation. This is teleport-style setup, not a collision-checked travel trajectory.

An accepted drop preserves base height/orientation and joint positions, holds joints, brakes wheels, and zeroes velocities. Scene objects stay in place. Physics time, encoder odometry, battery travel, and challenge history are not reset or advanced by placement. A new observation invalidates old commands, prior cached command results are cleared, and camera/pose snapshots refresh. `manual_placements` records operator intervention until reset; challenge completion in a repositioned episode is not evidence of autonomous performance. Neither placement coordinates nor intervention metadata enter `AgentObservation`.

## Predefined Challenge Checks

`backend/challenges.py` defines ten fixed presets, plus the unscored practice bench. Catalog category/difficulty are operator metadata. Their colored zones and room floor tints are visual-only markings shared by TinyRenderer and the spectator; they do not add a collision plane or support objects. Loading a preset reconstructs both authoritative and planning clients. Reset restarts the selected preset. `floor_size_m` defaults to 6 x 6 m, with each side constrained to 4-20 m. Warehouse uses 10 x 8 m; Service Gallery uses 8 x 8 m. Floor collision bounds, planning copies and spectator geometry share those dimensions; no floor/map coordinates are added to model observations.

Progress is evaluated on the worker at 20 Hz during motion and after each command. Placement requires a previous lift with the object's collision AABB bottom at least 0.08 m above the floor, while grasp-assisted or under real opposing finger contact. Completion requires release, the full horizontal AABB within the target, actual floor contact, linear speed below 0.025 m/s, and angular speed below 0.15 rad/s. Parking uses the combined chassis/wheel AABB with the same rest/contact tests. Basic parking/manipulation do not impose timed dwell; search and selected ordered-route objectives do. Their exact measurements and object identities are not part of `AgentObservation`.

Clinic and Warehouse use ordered objectives: only the current checkpoint can advance and at most one stage advances per update. Every checkpoint needs floor contact and full chassis/wheel containment; a transit checkpoint permits motion, while parking requires rest. Intermediate stages remain recorded. The final objective is re-evaluated each update and becomes incomplete on departure, loss of contact or motion. Optional `dwell_s` (0-10 s, default zero) accrues only on eligible simulation updates and resets when conditions fail; repeated observations at the same simulation time do not add dwell. Warehouse dispatch requires one second. Operator placement can still satisfy physical regions and is explicitly marked as intervention; these checks do not prove autonomous routing.

Warehouse has two offset rack rows with shelves, uprights, stock boxes, lane markings, packing equipment and dispatch terminal. Its blue/orange/green ordered route is verified by real wheel commands over 20 m. Service Gallery has electrical cabinets, vents, tanks, valves, partitions and red/yellow inspection stations; it reuses the search camera/frustum/ray and stationary-dwell evaluator below. The verified wheel route visits the decoy before the target and exceeds 15 m. Workshop adds fixed fixture blocks, a divider, parts shelves, bins, a counter and vise around the existing two-arm cube geometry. Both physical pickup/release routes pass with static fixture poses unchanged, using the standard assisted-grasp approximation. This is not a physical-only learned-policy result.

The clinic description now calls the colored panels landmarks and explicitly excludes carrying supplies: no supply payload or sign-reading classifier exists. Its two private route gates and final bay are verified; final parking is no longer permanently latched. None of the new grounds adds a semantic room classifier or target coordinates to text/voice input.

The return-to-charge preset adds a staged simulated energy budget. Charge starts at 100%, drains by 4 percentage points per meter of wheel-encoder travel plus 0.1 per simulated second off the stationary charger, and recharges at 20 points per simulated second while fully parked on the original pad. One second of stationary survey-zone occupancy applies a one-time 60-point scan cost. Low battery is 35% or below. Survey completion and low-battery return are recorded; final success requires at least 90% while still docked. Charge is clamped to [0,100], and zero charge rejects movement and interrupts an in-flight movement at the next battery update. Stop remains independently interruptible at every physics tick.

Battery state advances only with physics, including the bounded `wait` action (up to two seconds); inference latency, feedback delays, and repeated observations do not recharge or drain it. `wait` brakes and holds all joints, obeys Stop, and uses the same stale-command/deduplication rules as movement. The battery sensor exposes only `charge_pct`, `low`, and `charging`. This is a scaled challenge mechanic, not an electrical, thermal, or battery-chemistry simulation.

Apartment Search is a fixed three-room flat with two 1.3 m doorways, collision walls, simple furniture, an 18 cm yellow cube on a 34 cm pedestal, and a red distractor. Its private `search_target` selects a body; no target zone is rendered. An overhead spectator view exposes the layout only to the operator. Door openings have no movable leaves or headers, keeping the roofless layout readable.

The search evaluator requires planar base-to-target distance <= 0.9 m, floor contact, base speed < 0.025 m/s, angular speed < 0.15 rad/s, and both head-joint speeds < 0.05 rad/s. It samples five points around the target center: at least three must lie inside the actual head-camera frustum with a 5% edge margin, and their first physics ray hit must be the target. Conditions must hold for one continuous simulated second; a failed check resets dwell. Repeated observations or wall-clock inference delays cannot satisfy it. These private measurements never enter `AgentObservation`. This is a curated geometric visibility test, not semantic image recognition or a generalized object-finding benchmark.

Kitchen to Bathroom reuses the apartment walls and open doorways with different room furnishings. Its private `initial_xy` starts both physics clients at [1.1, -1.5] m facing the kitchen appliances, with head pitch 0.12 rad. Clinic, Warehouse and Service Gallery also specify private starting positions; other presets retain [0, 0]. Settling still resets simulation time and encoder odometry to zero. Fixtures are static boxes and cylinders with matching visual/collision shapes; explicit allowlisted material overrides assign tile and fabric using the existing bitmap textures. The toilet bowl/seat, burners, and faucets use cylinders. The mirror-like panel is a flat colored surface, not a reflection renderer.

The bathroom objective has `visible_zone=false`, suppressing its marker while retaining private AABB scoring. Its clear arrival region is centered at [1.40, 1.15] m with size [1.20, 1.48] m. The full chassis/wheel AABB must fit, with actual floor contact, linear speed < 0.025 m/s, and angular speed < 0.15 rad/s. No dwell or head orientation is required, and leaving clears completion. Initial pose, fixture names, room identity, arrival coordinates, and evaluator progress are absent from model observations and text/voice instructions. The public goal asks for visual room identification; this preset scores physical arrival, not the correctness of a natural-language room description.

## Assisted Grasp Approximation

Closing does not select a nearest object. A candidate must be movable, no more than 0.35 kg, and at most 0.11 m in each dimension. Both finger links must exert contact on that same body, their contact normals must oppose (dot product <= -0.7), and its center must lie within the configured palm enclosure.

Only then is a fixed constraint created at the existing relative transform. No object pose is reset or teleported. Object collisions remain active. The constraint is force-limited to 18 N; measured overload or separation beyond 0.12 m drops the object. Opening above 0.065 m releases the constraint. This opening threshold is currently calibrated for the 0.06 m demo cube, not a general release policy for all possible object sizes.

Agent-facing gripper sensors contain only aperture, two contact booleans, and load, never body IDs, names, colors, or poses. `contact_physics` is not offered.

## Remaining Mechanical Risks

- Current collision preflight checks moving links against scene bodies, chassis, torso, head, shoulder brackets, and the opposite arm. Same-arm nonadjacent self-collision coverage and carried-object swept-volume checks need expansion.
- Support spheres approximate low-friction casters; they are not articulated caster assemblies.
- Only the curated cube dimensions, mass, floor positions, and tested motions are verified. General ground workspace, random scene validation, stability margins, and load/drop stress tests remain open.
- No persistent action journal exists yet; action deduplication is per live episode and exact duplicate IDs return the prior result.
- The operator state endpoint is privileged; only `AgentObservation` is intended for future model adapters.
- The API is a local prototype with same-origin checks, not a production authentication boundary.
