**Robot power and bounded Luna usage candidate (2026-09-15):** `robot-power-v1` tests the hypothesis that explicit Off/On-idle/Working states, local idle throttling, no camera-triggered inference and bounded model usage reduce unnecessary processing while preserving motion authority. Power-off immediately interrupts the controller, revokes motion through the existing Stop revision, drains/cancels work, invalidates pending spatial jobs, suspends capture and unloads resident SmolVLA. Power-on preserves the scene/maps and starts no old task. A newer Stop during power-on prevents pending resume; Off survives episode reset. Startup remains On/idle for compatibility, and power state is not persisted. Stop remains independent of power.

Idle RGB/depth and home sensor submissions are limited to a 2 s interval, preview submissions use the idle interval when requested, WebSocket state publication slows from 50 ms to 1 s, and map polling uses 2 s idle / 5 s Off intervals. The map labels deliberate reduced-duty operation Idle while retaining real sensor errors and stale guards. No freshness/clearance thresholds are relaxed; active navigation still requires fresh footprint evidence. This is reduced submission cadence, not a measured CPU/GPU reduction or complete suspension of all UI rendering. Legacy text and voice camera-triggered wake-ups are removed; explicit voice input remains available without automatic recording.

Every text model call now passes through a controller budget adapter; voice responses use equivalent gates. Request counts increment before submission, including failed/cancelled attempts. Browser defaults are 12 requests / 100,000 reported input+output tokens; API defaults are 30 / 100,000. Request/token settings persist, and mid-task redirects retain counters and the original limits. Unknown response usage ends the task. Token thresholds are checked after usage is returned and may overshoot by one response; cancelling an in-flight request does not guarantee zero provider billing, and usage for such a request may remain unknown. This is not an exact monetary cap. After an approved plain-exploration plan, bounded local exploration continues without repeated model checkpoints; semantic object/room paths remain model-guided. The existing first-plan dependency, timeout/403 handling, and active sensor latency are not fixed.

## Nav2 Primary Integration

Follow-up evaluation: the task pilot and local comparison above supersede any implication that the initial two-goal integration establishes a performance improvement. The hypothesis that Nav2's tracker reduces short-goal arrival time remains unproven. Local probes kept 0.7 m / 1.2 m targets, two repeats per backend, reversed order on repeat two, enhanced rendering and a common 0.04 m position criterion. They were operator-selected scripted goals with 60-second local deadlines, not the 180-second real-model task pilot. Different speed caps, additional Nav2 laser and final-heading validation are disclosed; no software or safety threshold was adjusted to produce a win.

The real-model attempt ran from 21:17:31.989 to 21:18:57.059 +02:00; Built-in parking's retained recording lasted 35.656 s before access failure and has zero model tokens. The local attempt ran from 21:21:54 to 21:26:14 +02:00 and is marked `source_changed_during_run=true`. At inspection, differences included the app, worker, continuous supervisor, contracts and home-mission source; these were not edited for this comparison. No conclusion attributes a failure to a particular concurrent change. After preserving all eight results, the runner's post-scan readiness and final-drift handling were corrected and checked without another motion trial. Readiness passed; source freeze failed again. Further evaluation is blocked, not complete qualification. The original port-8013 run `9fa6785a-9335-4101-9001-7144285d3703` remains inactive, not busy and stopped; all task-owned pilot containers were removed.

Design: `nav2-supervised-v1-integration`, architecture `nav2-supervised` 0.1.0. Hypothesis: a proven Nav2 planner/controller can replace local destination tracking while semantic selection and motion authorization remain local. The original controller is explicitly selectable as backup; API default remains built-in for compatibility, and the UI prefers Nav2 when launched with `-Nav2`. No automatic switch occurs after Stop or failure. Affected scenarios: bounded local destinations in continuous supervision; parking was only an integration fixture. Apartment search, target recognition, task completion, dynamic obstacle navigation and real-model behavior are **not measured** for Nav2.

Nav2 uses odometry-frame rolling costmaps, regulated pure pursuit, velocity smoothing and collision monitoring. Camera/depth and synthetic laser contain no object identities or privileged geometry; the additional laser means a future built-in comparison must match or disclose sensor differences. Existing candidate generation, scans, turn and marked-floor approach remain. Composed routes, furniture circuits and rolling continuation require explicit built-in selection. ### Version Rules

- [Architecture registry](../backend/experiment_variants.py): each supported controller family starts at semantic version `0.1.0` when this tracking scheme is introduced. This is a new provenance baseline, not a retroactive version assigned to earlier experiments. The historical AI-waypoint registry entry does not imply that the current API supports it.
- Architecture identity is `family@major.minor.patch+revision`, for example `observed-continuous@0.1.0+47fc5f0cc16e` for the final preview. The 12-character revision is derived from the full SHA256 mapping of backend Python sources, robot URDF and project metadata. Any covered source change updates the revision even when the human-managed semantic version is unchanged.
- Bump patch for a compatible correction within the design, minor for an added/changed control strategy or observation/tool capability, and major for incompatible control/observation contracts. Every intentional design change also receives a ledger label, hypothesis and evidence entry here. Never change archived labels or reports to make a newer result appear comparable.
- Model/configuration identity has a separate revision over provider, profile, deployment and relevant settings: reasoning, image/context/feedback settings, effective turn/time budget, handoff/adaptive controls, camera-history mode and applicable local-policy configuration. Changing the task does not change model identity; the task fingerprint is separate. No credentials enter these records. The combined variant ID joins architecture and model revisions.
- Legacy rows remain explicitly unversioned. A deployment name is not proof of underlying model identity. Endpoint revisions, cloud randomness and local checkpoint weight hashes are not pinned by this model ID; checkpoint names/paths are recorded where applicable. Underlying identity remains marked unverified.

Implementation hashes describe covered files on disk at session start, with end-of-session drift checks. They do not prove that a long-running Python process imported those exact bytes after source edits. Restart the backend after changes; use labelled frozen-code evaluator runs with matched tasks/settings and recorded runtime workload before claiming improvement. Interactive sessions are not controlled benchmarks. The new architecture fingerprint does not cover frontend renderer bundles/textures or dependency binaries; existing CLI design/build snapshots provide additional provenance. GUI and CLI representations of local checkpoint settings may differ, so their IDs are not an automatic equivalence guarantee.

## Decision Rules

Primary: physics-verified success rate per challenge with every planned attempt visible. Also record false completion claims and contact episodes. Compare successful completion times only alongside success rates; an early failure is not a speed improvement. Inspect paired outcomes and distributions, not just an aggregate average.

Secondary: travel distance, input/output tokens, images sent, inference latency, rescans/recovery, and stale-sensor stops. Dollar cost needs verified model pricing; tokens alone are not dollars. Similar frame counts do not imply similar image-token charges.

To claim improved brief-object recognition, use annotated fixed recordings or explicit target-visibility events and score missed sightings and false identifications separately. Task success alone does not isolate perception. Only promote a change after repeatable gains with no unacceptable safety/retention regressions; otherwise mark mixed, regressed or inconclusive and retain the baseline.
