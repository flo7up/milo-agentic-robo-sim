# Robot Lab Development

This project uses the microsoft-foundry skill for local model control. Before working on or answering questions about Foundry agents, read the microsoft-foundry skill. If you are in VS Code, read the vscode-microsoft-foundry skill first.

- This is a local FastAPI/PyBullet application using the OpenAI Responses SDK, not a hosted Foundry agent. Preserve its architecture; do not provision cloud resources or scaffold azd without a user request.
- Run physics tests with `./.runtime/env/python.exe -m pytest -q` on this Windows setup.
- Frontend: `npm --prefix frontend run build`, then `npm --prefix frontend test`. Playwright owns an isolated port-8001 fixture using real physics and scripted inference. It does not contact Foundry.
- Use the CFS-protected npm feed `https://packagefeedproxy.microsoft.io/npm/`. Do not bypass blocked registries.
- Never read or print credential-bearing environment values. The app supports backend/.env and root .env; existing process variables take precedence.
- Keep model inputs restricted to AgentObservation and the corresponding head-camera image. An additional observed-map image may render only the typed AgentObservation.observed_map sensor snapshot, with its frame, age and revision; never render spectator/evaluator geometry. Never execute tools outside the validated worker.
- Stop, takeover, reset, and disconnect must invalidate pending model motion. Keep inference serialized and feedback interval changes effective during waits.
- Label scripted tests separately from real-model validation. A configured deployment name does not establish the underlying model identity or benchmark success.
- Default new real-model navigation evaluations to Qwen (none reasoning) with Luna task supervision (low reasoning). This hybrid is the main development configuration. Keep scripted tests model-free and preserve explicitly requested single-model/legacy diagnostics; never silently fall back when either model is unavailable.
- Maintain `docs/DESIGN_PERFORMANCE.md` after every design change and evaluation: record hypothesis, design label, affected scenarios, artifact links, evidence type, measured outcomes and limitations. Use labelled, frozen-code evaluator runs and matched settings for improvement claims; preserve failures and mark untested effects as not measured. Do not pool scripted, operator-assisted and real-model evidence.
- Evaluate navigation/control changes against a complete fixed baseline series. Use `scripts.benchmark_household --stage run --baseline <existing-run> --design <candidate-label> --output <new-directory>`; use `--establish-baseline` only for an explicitly new series. Ad-hoc probes remain diagnostics, not replacement benchmark results. Never revise suite/map/scoring inputs to make a candidate appear improved.
- Keep local exploration independent of Luna inference. A clear beam alone does not authorize motion: require the observed footprint corridor, fresh sensors and worker safety checks. Saved-map reuse is optional; skipping reuse must never delete or overwrite a previous map.
